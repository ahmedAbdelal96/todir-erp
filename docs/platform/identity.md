# Identity and sessions

Each account belongs to exactly one tenant for its entire lifetime. The tenant owns one globally unique login domain; the backend parses the domain from the submitted email, resolves the active tenant through the controlled routing function, establishes tenant context, and loads the account by tenant plus normalized full email. There is no global human identity, cross-tenant account, organization-selection challenge, or tenant-switching session. A company administrator provisions accounts from name, email prefix, and tenant-local roles; the backend constructs the full login email and returns a cryptographically strong temporary password once. Initial password change is a short-lived continuation state, followed by MFA when enabled, then a cookie session bound to the exact account and tenant.

Browser sessions use secure, HttpOnly, SameSite cookies. Passwords use the approved salted password hash format, failed-password lockout is five attempts for fifteen minutes, and session validation checks the tenant-bound account security stamp. MFA uses TOTP with protected secret material and one-time recovery-code digests; enabled accounts must provide a valid challenge-bound code. Authentication challenges persist only a SHA-256 token digest, identity, next step, expiry, attempt count, and consumption state; they contain no password, MFA secret, or selectable tenant. Company-admin password reset generates a new temporary password, sets `MustChangePassword`, invalidates sessions/challenges, and returns the password once. Login-domain changes use a dedicated MFA-protected atomic operation that updates every account email and invalidates affected sessions/challenges. Access tokens are never stored in browser local storage.
