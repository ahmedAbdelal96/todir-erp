# Authorization

Modules own their permission catalog through manifests. Roles contain permission entries and the tenant-bound authorization subject receives roles at Tenant, Legal Entity, or Branch scope. A permission is effective only when the same role is assigned to the current membership, owned by the current tenant, active, applicable to the requested resource scope, and explicitly owns that permission; another active role can never activate an inactive role's permission. Backend authorization is authoritative; frontend checks only shape navigation and affordances. The permission authorizer deliberately keeps no process-wide decision cache: each request evaluates the freshly loaded PostgreSQL subject so role, assignment, lifecycle, and revocation changes cannot remain effective because of stale authorization state. Request-scoped subject reuse is limited to the current HTTP request and tenant/membership pair.
