# HR operations and recovery

Before migrating an entity, configure `PUT /api/v1/hr/legal-entities/{legalEntityId}/go-live`; use the current `version` as `expectedVersion` on changes. The API records an audit entry. `EmployeeMigrationStrategy` is `ActiveOnly` or `ActiveAndHistorical`; the first rejects ended/terminated employee import rows. `AttendanceHistoryBoundary` is the approved cutoff date through which historical attendance may be included; `null` means no historical attendance migration. `LeaveOpeningBoundary` is the effective date of the approved opening entitlement; leave opening imports must match it exactly, and `null` disables opening imports. `LeaveHistoryBoundary` is the oldest historical leave-request date included; `null` means historical leave requests are not migrated. `DocumentMigrationStrategy` is `None` or `AllAvailable`; the latter permits importing ready Files references and metadata.

Legacy compensation history uses `POST /api/v1/hr/imports/compensation/preview` followed by `/commit`. Keep the approved source file and its SHA-256, mark missing source facts `Partial` or `UnknownHistory`, and use the same source system plus legacy agreement ID for idempotent replay. The import does not calculate net pay, alter Payroll snapshots, or fabricate a contract link; a provided legacy contract ID must already resolve through the contract import reference.

Legacy insurance records use `POST /api/v1/hr/imports/insurance/preview` followed by `/commit`. The source row may carry the member number, but the importer encrypts it before persistence and returns no unmasked value; audit/event payloads contain only the masked suffix. Keep source quality explicit and avoid reusing a legacy enrollment ID for a changed payload.

Legacy employee documents use `POST /api/v1/hr/imports/documents/preview` followed by `/commit`. Each file must already be a ready Platform Files reference authorized for the resolved employee, with a classification that permits the requested sensitivity. Import stores verified file metadata, starts document verification as `Pending`, and records the legacy source and quality; it does not upload bytes or bypass Files access controls.

This runbook applies to the `business_hr` module. HR records are tenant scoped and most employment facts are also legal-entity scoped. Use the supported HR command/API for corrections so the module writes the required history and audit evidence. Do not repair business rows with direct `UPDATE` or `DELETE` statements.

## Before diagnosing a case

1. Confirm tenant, legal entity, employee, employment, effective date, and correlation/request ID.
2. Confirm the actor's HR permission and legal-entity scope. Do not widen scope to make a lookup work.
3. Read the employee timeline, employment history, related source record, and audit entry.
4. Preserve the original evidence. Use an append-only correction or a new effective-dated record.
5. Record the incident and corrective command reference. Reconcile downstream Payroll only through its supported correction path.

## Operational cases

| Case | Diagnosis | Supported correction |
| --- | --- | --- |
| Suspected duplicate employee | Compare normalized Arabic/English names, identifiers using the restricted reveal flow, and employment history. | Keep both identities until HR confirms the person. Use the approved duplicate merge workflow when available; do not delete either employee or repoint a login by editing the database. |
| Wrong User link | Verify the employee, active membership, expected employee version, and audit history. | Use `PUT /api/v1/hr/employees/{employeeId}/membership` with the dedicated tenant-scoped `hr.employee.link_user` permission, the expected version, and a reason. HR reassigns only the employee-to-membership link, writes an effective-dated event and audit entry, and rejects inactive or already-linked memberships. Do not edit HR or IAM rows directly. |
| Employee migration import | Preview the source-system code, stable legacy employee IDs, batch reference, SHA-256 file hash, and each row's quality classification. Review row validation, resolved initial branch/department/position/manager references, cycles, existing source links, and possible duplicate warnings before commit. | `POST /api/v1/hr/imports/employees/preview` then `/commit` creates employee + initial employment and optional initial assignment rows, with durable legacy references. Replaying an identical legacy row is idempotent; changed payloads are rejected. |
| Historical assignment migration | Preview the stable legacy assignment IDs, source employee references, effective dates, organization codes, and manager references. Assignment end dates are exclusive. | `POST /api/v1/hr/imports/assignments/preview` then `/commit` imports bounded effective-dated rows with per-row idempotency, source references, history events, and audit. Correct rejected codes/dates in the source and preview again; do not delete an imported assignment to replay a changed row. |
| Contract history migration | Preview the source contract ID, employee reference, dates, status, and source quality classification. Missing start dates remain unknown; they are not replaced with the import date. | `POST /api/v1/hr/imports/contracts/preview` then `/commit` imports bounded active or historical contract rows with durable source references. Unknown start dates require `Partial` or `UnknownHistory`; only one active contract with unknown dates can exist for an employment until its dates are clarified. |
| Manager cycle | Follow manager assignments for the effective date until the cycle is found. Check the cycle guard and the employee's legal entity. | Assign a valid manager or remove the erroneous manager reference through the assignment workflow. Keep the prior assignment in history. |
| Contract activated incorrectly | Review the signed file reference, effective dates, amendment chain, and activation audit. | End or supersede the contract through the contract lifecycle API and create the correct contract/amendment. Do not rewrite signed terms or delete a contract. |
| Insurance enrollment awaiting review | Confirm the legal entity, employment, scheme, masked member number, effective dates, and registration evidence. A future or already-expired enrollment cannot be activated early. | Use the enrollment `activate` command with the current version after approval, or `reject` with a reason. Status changes are version-checked and audited; member numbers remain masked in normal responses. Draft enrollment evidence and terms are immutable after creation. |
| Document upload failed | Check Platform Files availability, file ownership, hash/size metadata, and request correlation ID. | Retry upload through Platform Files. Create the HR document record only after a valid FileRef is returned. Do not copy file bytes into HR storage or expose a reusable private URL. |
| HR document download denied or unavailable | Confirm active document status, `Verified` verification state, legal-entity scope, `hr.employee.document.read`, and `hr.employee.document.read_sensitive` for confidential, medical, or restricted records. Confirm the private Files bucket and browser-reachable `TODIR_FILES_PUBLIC_ENDPOINT` are configured. | Request `GET /api/v1/hr/employees/{employeeId}/documents/{documentId}/download?legalEntityId={legalEntityId}`. HR returns a five-minute URL only after authorization; absent, cross-entity, and sensitivity-hidden records return the same not-found response. Storage misconfiguration returns a service error. Never reuse an expired URL, persist it, or copy it into tickets, logs, or audit records. |
| HR document upload unavailable | Confirm the private MinIO/S3 bucket, `TODIR_FILES_*` settings, and local ClamAV service (`TODIR_FILES_SCANNER_HOST`, port `3310`) are reachable. Confirm the bucket expires abandoned `incoming/` objects after one day. | Create an owner-scoped upload intent, POST the file and every returned form field to its five-minute URL, then call the completion route. A Ready `FileRef` can then be attached through the existing employee-document endpoint. A failed or unavailable malware scan never makes the file downloadable. |
| Employee file shows missing required documents | Review enabled category requirements for the employee's legal entity, then check for an active, verified, unexpired document in each category. | Read `GET /api/v1/hr/document-requirements?legalEntityId={legalEntityId}` and `GET /api/v1/hr/employees/{employeeId}/document-completeness?legalEntityId={legalEntityId}`. Manage a category with `PUT /api/v1/hr/document-requirements`, supplying the current version and a reason. Disabled requirements do not make employee files incomplete; a pending or expired document does not satisfy an enabled requirement. |
| Leave carryover and expiry | Confirm the active leave policy effective on December 31, the January 1 cycle boundary, carryover cap, expiry months, immutable entitlement movements, and allocation rows. Balances are consumed FIFO by earliest expiry. | The clustered daily lifecycle job catches up missed annual boundaries and expires remaining carryover on its expiry date. A six-month carryover created on January 1 expires July 1. The job writes durable in-app HR reminders up to 30 days before expiry; retries are idempotent. Do not alter a movement or repair the ledger directly. |
| Other expiry reminders | Check the source contract, document, credential, insurance, probation, onboarding, or offboarding due date and the corresponding HR reminder row. | The clustered daily lifecycle job creates idempotent in-app reminders for due items and upcoming dates. Reminder persistence does not change the source HR record; external email/SMS/WhatsApp delivery is optional and is not required for HR state changes. |
| Repeated imported punch | Preview the source-system batch and resolve rejected rows before committing. Compare the immutable source reference, batch/row reference, payload hash, raw punches, and resulting normalized attendance record. | Retry the same batch through `/api/v1/hr/attendance/imports/commit`; an identical source row resolves to its existing punch and provenance reference. Conflicting source or row references are rejected. Correct a wrong normalized record with a reason; never delete raw punches. |
| Missing punch | Review the employee's assigned shift/calendar, raw punches, open exceptions, and local-time/DST interpretation. | Ask an authorized reviewer to add a correction with the source reason. Keep the missing-punch exception and original punches for audit. |
| Attendance normalization error | Review timezone snapshot, calendar, shift assignment, punch order, and normalization version. | Use the attendance correction command with a reason. A standalone normalization replay command is not available; do not edit derived minutes directly. |
| Payroll-locked correction | Confirm the Payroll snapshot/run and attendance lock reference. | Submit the authorized correction with the current attendance version and a reason. HR preserves the locked attendance, records the proposal as `PayrollDeltaPending`, and exposes the immutable correction delta to Payroll through the HR capability. Reconcile only against that snapshot; never unlock or mutate the consumed period. |

| Leave accrual failed | Check policy version/effective date, employment eligibility, the due period, existing immutable movements, and the Worker error with tenant/legal-entity scope. The daily HR lifecycle job catches up missing monthly or anniversary accrual periods, inserting at most 5,000 movements per legal entity per run. | Let the next daily run retry idempotently or use the authorized accrual command for a reviewed period. If the policy or source was wrong, create a reviewed balance correction movement; do not alter a movement or a projected balance. |
| Leave balance mismatch | Recalculate from immutable movements, including reservations, releases, taken, expiry, and correction entries. Check duplicated source keys. | Add a reasoned correction movement after HR approval and retain the reconciliation evidence. Never update a cached balance as the source of truth. |
| Payroll input sync failed | Compare snapshot ID, period, cutoff, payload checksum, and Payroll's consumed snapshot reference. | Retry the same snapshot request idempotently. Read pending locked-attendance corrections by snapshot through the HR Payroll capability; do not change an existing snapshot. |
| Termination/IAM mismatch | Compare effective termination date, employment status, linked membership, IAM membership status, and outbox delivery state. | HR publishes a deactivation request only after the last active employment ends. The Worker schedules it for the effective date, rechecks HR employment truth at execution time, then asks the IAM capability to revoke that membership, invalidate its existing sessions, and write the IAM audit entry. A transferred or rehired employee with active employment is not deactivated. Recover failed delivery through the supported outbox path; never write IAM storage from HR. |
| Scheduled termination remains pending | Check `terminationStatus`, effective date, employment version/status, and the Worker log for the legal entity. | The clustered daily HR lifecycle job applies due cases; a missed run is retried on the next run. A status/version conflict remains pending for HR review. Never force the status or `termination_applied_at` directly in PostgreSQL. Final-exit payroll facts appear only after the effective transition and for a period including that date. |
| Projection rebuild | Compare source event counts and employee counts with the affected projections. | Run `dotnet run --project backend/DbMigrator/DbMigrator.csproj -- --rebuild-hr-projections <tenant-guid>` with `TODIR_MIGRATOR_CONNECTION` set to a privileged maintenance connection. The command rebuilds the timeline and employee-list projections from HR-owned source rows in one transaction and writes an audit entry. It is tenant-wide; do not run it against a live database during normal business hours. Never rewrite projection rows manually. |
| HR report export | Confirm the user has report-read permission plus the separate export permission scoped to the legal entity; inspect the correlated `hr.report.exported` audit entry. | Attendance, leave-balance, and expiry reports export bounded UTF-8 CSV with spreadsheet-formula protection. Exports above 10,000 rows are rejected; narrow the date/report scope before retrying. Sensitive identifiers, document references, and restricted file metadata are excluded. |
| Restore/DR validation | Restore into an isolated recovery target; verify schema migration level, row counts, constraints, RLS, append-only guards, and tenant-specific reads. | Record the restore point, elapsed recovery time, and validation results. Never validate by restoring over the active development or production database. |

The PostgreSQL integration scenarios create synthetic records and intentionally leave audit/evidence rows in the disposable Development database. Run `HrPayrollDeltaIntegrationTests` and `HrMembershipDeactivationIntegrationTests` only against a disposable database that already has the canonical seed; set `TODIR_HR_TEST_DATABASE=1`, `TODIR_P04_ADMIN_CONNECTION`, and `TODIR_DATABASE_CONNECTION`.

## Safe repair rules

- Use semantic employee, employment, assignment, contract, attendance, and leave commands.
- Keep the original source and append a correction with actor, effective date, reason, and correlation ID.
- Never run support fixes such as `UPDATE employee SET salary=...`, `UPDATE leave_balance...`, `DELETE attendance_punch...`, or `UPDATE employment SET department=...`.
- A repaired fact does not rewrite a Payroll snapshot already consumed. Use Payroll's correction/delta workflow.
- If the supported correction path is missing, record the exact invariant and block only that repair until a reviewed command is added.
